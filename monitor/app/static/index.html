How the monitor sees your calls

The Luna apps still call luna-sentia-ollama:11434. That address now belongs to the monitor, which passes every request to Ollama unchanged and times it on the way back. It never stores prompts, images, or replies: only their sizes, token counts, and timings.

Ollama reports its own timings at the end of each reply. The monitor adds the wall time it measured itself, and splits every call into four parts:

Waiting
Wall time Ollama did not spend on this request: queued behind another request for the same model (Ollama runs Qwen3-VL one request at a time), plus decoding the request and preparing images. This is the part vLLM's batching removes.
Loading
Getting the model ready. Near zero when it is already in VRAM; seconds when Ollama had to load it, after it was unloaded for being idle or to make room.
Reading input
Processing the prompt, including encoding images for a vision model. Measured in tokens per second; fast, because every input token is processed in parallel.
Writing output
Generating the reply one token at a time. Usually the slowest part per token, limited by how fast the GPU can read the model's weights from VRAM for each token.

Models outside Ollama

Three apps run a model of their own, inside their backend, on the same GPU. Their work never passes through the monitor, so it is missing from the call timeline and the verdict; each app counts it instead, and the Inside the apps card asks them every ten seconds.

Luna Visia: SigLIP 2
Turns every image, and every search, into an embedding for meaning search. GPU only; it loads on the first image or search and stays loaded.
Luna Lexia: Docling
Reads each document's pages with its layout, table-structure, and OCR models before Qwen3-VL sees them. It uses the GPU while there is room and moves to the CPU when the GPU is short.
Luna Vibia: CLAP
Hears each track and turns it, and every search, into an embedding, with mood hints for the caption model. It runs on the GPU when there is one, with a CPU copy as a last resort.

For each, the card shows whether it is loaded and where, the GPU memory the app's process holds, and its calls and busy time since the app started. Those counts start again when an app restarts. Lexia's semantic search embeds with qwen3-embedding through Ollama, so that part is in the timeline.

The hardware charts

GPU utilisation
The share of time the GPU was running any work. It reads high while one request writes its reply, even though one request uses only a fraction of the GPU's compute. So a high number does not mean the GPU is full; it means it is never idle.
Memory bandwidth (in the GPU card's details)
The share of time VRAM was being read or written. Writing output is limited by this, which is why batching helps: several requests share each read of the weights.
VRAM
The solid line is everything on the card: Ollama's models, Visia's SigLIP, Lexia's Docling, Vibia's CLAP, and Windows itself. Under WSL the driver cannot split that by process, so the dashed line shows the share Ollama reports for its loaded models, and Inside the apps shows what each app's own process holds, as torch reports it.
Requests
The solid line counts requests in flight; the dashed line counts those waiting, estimated from Ollama's one-at-a-time limit per model (OLLAMA_NUM_PARALLEL). Waiting above zero means apps are queueing behind each other.
Power, temperature, and clocks
Power rises with how hard the GPU works. A hot GPU (above about 83 °C) lowers its clocks, which slows every request; the SM clock is the core speed.

Reading the pattern to decide on vLLM

vLLM is faster than Ollama mainly when several requests run at once, because it batches them. It also keeps a fixed share of VRAM reserved while it runs. So the decision rests on two questions the monitor answers:

  1. Do requests overlap? Look at the timeline: bars stacked in time across apps, long grey waiting segments, and a dashed waiting line above zero. If imports in Lexia, Fiora, Visia, and Vibia often run at the same time, batching has work to do. If bars sit end to end with gaps between them, it does not.
  2. Is there room? The least free VRAM during real use must leave space for vLLM's reservation on top of SigLIP, Docling, and CLAP. Under about 2 GB free, vLLM would starve the other models.

The verdict card weighs both with simple rules of thumb and shows its numbers. Leave the monitor running through a few real Drive and Gmail imports, ideally two apps at once, then compare the 24-hour and 7-day views.

Per-request speed matters too: output tokens per second on a single request is the baseline vLLM would have to beat when nothing overlaps.
